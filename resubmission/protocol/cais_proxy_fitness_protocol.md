\# CAIS Proxy-Fitness Validation Protocol



\## Purpose



This experiment evaluates whether repository similarity identified by the

MetaMatch + REDUX framework is associated with scenario-specific suitability

as a testing proxy for Critical AI Systems (CAIS).



Repository relatedness, software similarity, and CAIS proxy fitness are treated

as distinct constructs. MetaMatch and REDUX scores are not used as criteria in

the proxy-fitness rubric.



\## Anchors



Eight anchors are selected to represent distinct AI-system and supporting

infrastructure roles:



1\. apache/airflow

2\. huggingface/transformers

3\. ray-project/ray

4\. mlflow/mlflow

5\. ultralytics/yolov5

6\. serengil/deepface

7\. OpenBB-finance/OpenBB

8\. onnx/onnx



The cohort is selected for functional/domain diversity rather than observed

REDUX performance.



\## Candidate Population



For each anchor, evaluate the frozen MetaMatch top-5 candidate repositories

already generated by the existing retrieval pipeline.



Where feasible, include two additional control repositories whose functions

are not expected to provide strong support for the anchor-specific test

requirements.



No candidate may be removed because of an unexpected rubric or REDUX result.



\## Rubric Construction



Each anchor receives 4-6 scenario-specific testing requirements derived from

its functional role and plausible CAIS testing use.



Rubric requirements must be defined before candidate-level fitness scoring.



Candidate evidence is scored independently of MetaMatch rank and REDUX score.



Each requirement is scored:



0 = no evidence of support

1 = partial or indirect support

2 = strong/direct support



Proxy fitness percentage:



&#x20;   obtained rubric points / maximum possible points \* 100



\## Evidence



Rubric scoring may use publicly available repository documentation, README

material, architecture descriptions, documented features, tests, and other

repository evidence.



The evidence source supporting every nonzero rubric score must be recorded.



\## Adequacy Threshold



A candidate is considered scenario-adequate when:



1\. proxy fitness >= 60%, and

2\. no anchor-defined critical requirement receives a score of 0.



This threshold is fixed before candidate scoring.



\## Evaluation



For each anchor report:



\- candidate MetaMatch rank

\- REDUX similarity score

\- independent CAIS proxy-fitness percentage

\- adequacy decision

\- rubric dimension scores

\- supporting evidence



Across anchors report:



\- number and percentage of top-3 candidates classified scenario-adequate

\- number and percentage of lower-ranked candidates classified scenario-adequate

\- Spearman association between REDUX similarity and proxy-fitness score

\- high-similarity / low-fitness false-positive cases

\- lower-similarity / high-fitness boundary cases



\## Interpretation



A positive relationship supports the use of repository similarity as a

screening mechanism for candidate CAIS test proxies.



It does not establish functional equivalence between repositories or establish

that a candidate is universally suitable as a proxy.



Proxy suitability remains scenario-specific and must be established through

the independent rubric.
